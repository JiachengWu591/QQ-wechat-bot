# M0 风险验证

这些是一次性验证脚本，不是产品代码。按风险从低到高逐项验证，哪一步不通就先停下来调整方案。

M0 于 2026-11-03 收尾。API、QQ、iLink 和微信的主要流程都已跑通。第 13、14 项要别人配合，放到 M4 之前补测。

## 准备

把 `.env.example` 复制成 `.env.local` 并填写。`.env.local`、`.secrets/` 和 `output/` 都已被 git 忽略。不要把 key 命名成 `ANTHROPIC_API_KEY`，否则 Claude Code 可能改走 key，而 API 额度不覆盖 Claude Code。

## iLink 的连接和转发

- 重启监听后，连 `ilinkai.weixin.qq.com` 持续超时至少 16 次（`UND_ERR_CONNECT_TIMEOUT`）；随后 TCP 又能连通，约 400 毫秒，也没有开系统代理。原因不明，可能是跨境网络抖动，所以正式版要能自动重试，并在界面上显示通道状态。
- 微信的转发列表里选不到 ClawBot，所以无法把合并转发的聊天记录发给 bot。发文字和文件正常。

## QQ 全量群消息

群主在手机 QQ 里打开群，点机器人头像进入设置，把“机器人可获取的群聊消息范围”改成“获取群内全部消息”。改完后机器人要重新 Identify 才生效。

实测（2026-11-03）：所有群消息都走 `GROUP_MESSAGE_CREATE`，@ 消息没有再走 `GROUP_AT_MESSAGE_CREATE`，也没有重复推送。判断是否 @ 机器人用 `mentions[].is_you`。@ 消息的正文带 `<@机器人 openid>`，发给模型前要去掉。这次没有收到机器人自己回复的回声。

正式通道的实测（2026-11-04）：网关大约每小时下发一次重连要求（op 7），程序自动恢复，4 到 6 秒重新连上。连接中途真正断网的情况，真实环境还没有测到。

## 不要只看 apiKeySource

从 Claude 桌面应用的会话里启动子进程时，子进程会继承 `CLAUDE_CODE_*` 等变量并沿用桌面应用的登录。这时用一个无效 key 也能成功，`apiKeySource` 却仍然显示 `ANTHROPIC_API_KEY`。

所以 `01-agent-sdk.ts` 现在会清掉继承的认证变量，并提供 `npm run agent -- badkey` 用无效 key 做验证：只有它失败，才说明确实在用 key。正式引擎启动子进程时也必须这样清理。

## 判定标准

- **第 3、4 项：** `apiKeySource` 显示来自 key；Console 里能看到额度被扣。
- **第 5 项：** 在测试群 @ 机器人后，群里出现“M0 测试：已收到。”。如果连接因权限关闭，记下关闭码。
- **第 6 项：** 分别发文字、文件和一条合并转发的聊天记录，看 `output/ilink-msgs.jsonl` 里每种消息的结构。合并转发能否读到正文，决定长记录总结怎么做。
- **第 7 项：** 以微信里实际收到的消息为准，HTTP 200 不代表送达。
- **第 9 项：** 黑色像素接近 100% 表示截图失败。分别测试窗口在前台、被遮挡时的结果；最小化时截不到内容。让别人在测试群 @ 你一次，看“mention markers”是否大于 0。脚本不输出聊天文字，默认也不保留截图。
- **第 10 至 12 项：** 以你在微信里看到的结果为准。脚本报告未确认时，不会按回车。

## OCR 的限制

用生成的界面文字测过 56 个样本：放大 3 倍后，逐字完全正确的有 43 个（不放大时 22 个），宽松匹配 `@我` 为 14/14。低于 16 像素的小字仍不可靠。所以扫描 @ 用宽松匹配，宁可多提醒；发送前核对聊天对象用严格匹配，对不上就中止。真实微信界面的识别率要看第 9 项。

## 真实微信实测（2026-11-02）

- 窗口大小 1191×752，显示缩放 125%，窗口未激活。PrintWindow 成功，黑色像素 0%，整窗 OCR 约 0.6 秒，读出 33 行。
- 最小化时截不到内容。加 `-Restore` 可以不抢焦点地临时恢复再最小化，但窗口会短暂出现在屏幕上，不适合持续扫描。
- 整窗 OCR 跳过了顶部小字：所有行都在 Y≥101，读不到搜索框和聊天标题，所以标题要单独裁剪读取。搜索框文字裁剪后、提高对比度后仍读不出。
- 聊天标题：裁剪后灰度化并提高对比度，能逐字读对“文件传输助手”，不处理时有 2 处差异。但对比度处理会让生成的测试图读错，整窗读出的行数也从 33 至 41 行降到 19 行，所以两种方式都读，任一种逐字匹配就算通过。
- 文字改为逐字符模拟键入，不经过剪贴板：最初的粘贴方案在剪贴板里有图片或文件时无法恢复内容，所以放弃。文本含换行时会拒绝，因为换行在微信里等于发送。
- 整窗 OCR 读不到输入框里的文字，英文和中文都一样，所以搜索框和输入框改成单独裁剪读取。
- 搜索切换：Ctrl+F 后键入的名字确实进了搜索框（只读核对，Y=63），没有进输入框，但读回来差 2 至 3 个字，严格匹配未通过，脚本没有按回车。判定改为允许差一半字符后重测通过：回车后打开了聊天，严格的标题核对也通过。这个宽松判定只用来判断文字落在哪个框。
- 左栏和标题栏不随窗口缩放（窗口 1191 和 976 宽时，标题都在 X=382），所以区域划分改用固定宽度。如果手动拖动过左栏宽度，这个假设要重新验证。
- 窗口被其他窗口遮挡时能否截图、OCR 文字是否准确、真实的 @ 标记能否识别，都还没验证。要判断准确度，可以加 `-Keep`，自己对比截图和 `output/wx-ocr.txt`。
