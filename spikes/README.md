# M0 风险验证

这些是一次性验证脚本，不是产品代码。按风险从低到高逐项验证，哪一步不通就先停下来调整方案。

M0 于 2026-11-03 收尾。API、QQ、iLink 和微信的主要流程都已跑通。第 13、14 项要别人配合，放到 M4 之前补测。

## 准备

把 `.env.example` 复制成 `.env.local` 并填写。`.env.local`、`.secrets/` 和 `output/` 都已被 git 忽略。不要把 key 命名成 `ANTHROPIC_API_KEY`，否则 Claude Code 可能改走 key，而 API 额度不覆盖 Claude Code。

## iLink 的连接和转发

- 重启监听后，连 `ilinkai.weixin.qq.com` 持续超时至少 16 次（`UND_ERR_CONNECT_TIMEOUT`）；随后 TCP 又能连通，约 400 毫秒，也没有开系统代理。原因不明，可能是跨境网络抖动，所以正式版要能自动重试，并在界面上显示通道状态。
- 微信的转发列表里选不到 ClawBot，所以无法把合并转发的聊天记录发给 bot。发文字和文件正常。

## QQ 全量群消息

群主在手机 QQ 里打开群，点机器人头像进入设置，把“机器人可获取的群聊消息范围”改成“获取群内全部消息”。改完后机器人要重新 Identify 才生效。

实测（2026-11-03）：所有群消息都走 `GROUP_MESSAGE_CREATE`，@ 消息没有再走 `GROUP_AT_MESSAGE_CREATE`，也没有重复推送。判断是否 @ 机器人用 `mentions[].is_you`。@ 消息的正文带 `<@机器人 openid>`，发给模型前要去掉。这次没有收到机器人自己回复的回声。

正式通道的实测（2026-11-04）：网关大约每小时下发一次重连要求（op 7），程序自动恢复，4 到 6 秒重新连上。连接中途真正断网的情况，真实环境还没有测到。

## 不要只看 apiKeySource

从 Claude 桌面应用的会话里启动子进程时，子进程会继承 `CLAUDE_CODE_*` 等变量并沿用桌面应用的登录。这时用一个无效 key 也能成功，`apiKeySource` 却仍然显示 `ANTHROPIC_API_KEY`。

所以 `01-agent-sdk.ts` 现在会清掉继承的认证变量，并提供 `npm run agent -- badkey` 用无效 key 做验证：只有它失败，才说明确实在用 key。正式引擎启动子进程时也必须这样清理。

## 判定标准

- **第 3、4 项：** `apiKeySource` 显示来自 key；Console 里能看到额度被扣。
- **第 5 项：** 在测试群 @ 机器人后，群里出现“M0 测试：已收到。”。如果连接因权限关闭，记下关闭码。
- **第 6 项：** 分别发文字、文件和一条合并转发的聊天记录，看 `output/ilink-msgs.jsonl` 里每种消息的结构。合并转发能否读到正文，决定长记录总结怎么做。
- **第 7 项：** 以微信里实际收到的消息为准，HTTP 200 不代表送达。
- **第 9 项：** 黑色像素接近 100% 表示截图失败。分别测试窗口在前台、被遮挡时的结果；最小化时截不到内容。让别人在测试群 @ 你一次，看“mention markers”是否大于 0。脚本不输出聊天文字，默认也不保留截图。
- **第 10 至 12 项：** 以你在微信里看到的结果为准。脚本报告未确认时，不会按回车。

## OCR 的限制

用生成的界面文字测过 56 个样本：放大 3 倍后，逐字完全正确的有 43 个（不放大时 22 个），宽松匹配 `@我` 为 14/14。低于 16 像素的小字仍不可靠。所以扫描 @ 用宽松匹配，宁可多提醒；发送前核对聊天对象用严格匹配，对不上就中止。真实微信界面的识别率要看第 9 项。

## 真实微信实测（2026-11-02）

- 窗口大小 1191×752，显示缩放 125%，窗口未激活。PrintWindow 成功，黑色像素 0%，整窗 OCR 约 0.6 秒，读出 33 行。
- 最小化时截不到内容。加 `-Restore` 可以不抢焦点地临时恢复再最小化，但窗口会短暂出现在屏幕上，不适合持续扫描。
- 整窗 OCR 跳过了顶部小字：所有行都在 Y≥101，读不到搜索框和聊天标题，所以标题要单独裁剪读取。搜索框文字裁剪后、提高对比度后仍读不出。
- 聊天标题：裁剪后灰度化并提高对比度，能逐字读对“文件传输助手”，不处理时有 2 处差异。但对比度处理会让生成的测试图读错，整窗读出的行数也从 33 至 41 行降到 19 行，所以两种方式都读，任一种逐字匹配就算通过。
- 文字改为逐字符模拟键入，不经过剪贴板：最初的粘贴方案在剪贴板里有图片或文件时无法恢复内容，所以放弃。文本含换行时会拒绝，因为换行在微信里等于发送。
- 整窗 OCR 读不到输入框里的文字，英文和中文都一样，所以搜索框和输入框改成单独裁剪读取。
- 搜索切换：Ctrl+F 后键入的名字确实进了搜索框（只读核对，Y=63），没有进输入框，但读回来差 2 至 3 个字，严格匹配未通过，脚本没有按回车。判定改为允许差一半字符后重测通过：回车后打开了聊天，严格的标题核对也通过。这个宽松判定只用来判断文字落在哪个框。
- 左栏和标题栏不随窗口缩放（窗口 1191 和 976 宽时，标题都在 X=382），所以区域划分改用固定宽度。如果手动拖动过左栏宽度，这个假设要重新验证。
- OCR 文字是否准确、真实的 @ 标记能否识别，都还没验证。要判断准确度，可以加 `-Keep`，自己对比截图和 `output/wx-ocr.txt`。

## 遮挡和滚动（2026-11-05）

- 遮挡：窗口 1264×781，25 个采样点全被盖住，手机发的消息在截图的聊天区读到了，黑色像素 0%。只盖住一部分的窗口本来就会刷新，所以要盖满才算数。微信有焦点不代表没被盖住：当时豆包窗口盖在有焦点的微信上面。
- 滚动：完全被盖住时，用 PostMessage 发 WM_MOUSEWHEEL 就能滚动，焦点和光标都不变（5 轮里 4 轮光标没动，另一轮用户当时在用鼠标，还要再看）。
- 每条消息固定滚约 62 像素（125% 缩放），和 delta 大小无关：delta 600 和 3600 走的距离一样。要翻一页就连发多条。
- 连发 6 条（间隔 40 毫秒）时，每步走 323 到 425 像素，消息区约 469 像素，重叠 9% 到 31%，距离并不固定。滚回去后和起点差 1.9%，也不是精确回到原处。所以读多屏不能靠算距离对齐，要靠屏幕之间的重叠内容去重，每页最好只发 4 到 5 条。
- 连滚 25 步（约 1500 像素）还没到顶，到顶后的表现未测。

## @ 标记和切换聊天（2026-11-05）

- @ 标记：微信被完全盖住时，原图和提高对比度两种读法都逐字读到“有人@我”，位置在左栏（x=157，y=140），群名就在它正上方，所以能对应到是哪个群。只测了一个样本。打开这个群后标记消失，所以程序不能靠逐个打开聊天来确认 @。
- 标题的 OCR 不稳定：文件传输助手的标题在 3 倍及以上放大时，两种读法都差 1 个字；提高对比度后放大 1 倍或 2 倍才逐字正确。所以标题要多读几种设置，任一逐字匹配算通过。这也有风险：名字只差一个字的两个群可能被读混，正式版要处理。
- 群标题带人数：这个群读出来是 5 个字符（“测试”加人数），核对时要去掉人数。
- 两个字的名字打进搜索框后，读回来两个字都不对，不能靠读搜索框判断文字落在哪。搜索结果弹窗是单独的 Qt 工具窗口（类名以 `QWindowToolSaveBits` 结尾，460×705，盖在左栏上），它出现才是可靠的信号。
- 搜索加回车打开了“测试”群，标题核对通过。切回文件传输助手时，回车打开了“搜一搜”（WeChatAppEx，微信内置浏览器），主窗口还停在“测试”群，没有发出任何消息。
- 原因：回车打开弹窗里高亮的第一行，而第一行不一定是聊天。搜“测试”时高亮带在 y=50 到 130，正好是群（x=100，y=81）。搜“文件传输助手”时高亮带在 y=50 到 93，是一行搜一搜的建议（x=47，y=62），建议有 5 行，真正的聊天排在 y=333。高亮颜色是 237,237,237，其他行是 250,250,250，所以回车前可以核对高亮带里是不是这个名字。标题核对只能发现打开错了，防不住已经打开的网页。
- 弹窗右边有透明边，PrintWindow 截出来是黑的，内容右边缘在 x=429（窗口宽 460）。
- 点左栏：向主窗口 PostMessage 发 WM_MOUSEMOVE、WM_LBUTTONDOWN、WM_LBUTTONUP，能打开那一行的聊天。当时微信被盖住 20/25 个采样点，焦点一直在别的窗口，打开后标题核对通过，@ 标记消失。完全盖住时还没试点击（滚轮试过）。这一轮脚本在切回前就停了，所以没有读到光标是否移动的结果。
- 第二个 @ 样本：在第 4 行（y=391），两种读法都逐字读到标记，群名也在正上方读对了。
- 左栏只读得到可见的约 8 行：第一次让对方 @ 时这个群不在可见范围，标记和群名都读不到。排下去的聊天要滚动左栏才能发现。
- 没有未读标记、也不在第一屏时，每一行都读不出“测试”（裁出名字单独读，12 种设置都不对），但这个群当时确实不在可见范围，所以这不算 OCR 的错。正在打开的那一行也读不出名字，文件传输助手也一样，所以不能靠读左栏的名字切回去。
- 用户手动最小化后截不到内容。用 ShowWindow 的 SW_SHOWNOACTIVATE 恢复不抢焦点，但窗口会出现在屏幕上。
- 2026-11-05 第三次让对方 @ 时，左栏这一行的预览带 @，但没有“有人@我”，所以没有触发。用户退出手机上的群、让对方从成员列表选人后，标记就出现了，具体是这两个原因中的哪一个没有分开试。
- 同一行的“有人@我”，OCR 有时读成从中间开始（y 也差 5 像素），所以不能按标记的起始位置找群名，要按左栏文字列的固定位置（125 个逻辑像素）找。
- 第一次完整流程（06:18，Haiku）：盖住 25/25，点开、核对标题、截图到读完 13 秒，$0.0008，焦点和光标都没动。这个群历史很短，第 2 屏就到顶了，到顶判断正确。
- 多屏去重（Haiku，$0.0009）：群里有编号 1 到 20 的消息和最后一条 @，读 3 屏得到 9 到 20 和那条 @，共 13 条，顺序对，没有漏，也没有重复。每屏约 47 KB。所以 3 屏大约覆盖最近 13 条，更早的读不到。
- 输入框（125% 缩放，窗口高 782）：是一张圆角卡片，内部第 588 到 755 行，上下边是浅色细线。表情图标和发送按钮在卡片底部（第 713 到 745 行），打字区在它们上面。卡片下面还有约 27 像素的渐变和阴影，所以不能从窗口底部往上找第一个颜色变化。这个错误曾让截图把输入框也截进去。
- 发送演练（走完全部检查，打字后不按回车，再清空）：群已打开时 2.8 秒，用搜索打开时 7.1 秒。都通过，没有发出消息。用搜索打开后，切回原窗口一次可能不成功，所以要重试。
- OCR 读输入框和绿色气泡都很差：`枢发送测试2` 在七种设置下读成 `枢发选劐讠酲`、`枢发这则`、`气都试2` 等，每次都不一样，“测”尤其读不准。所以不能整串比对，只能问“草稿里至少一半的字有没有在几种读法里出现过”。这只能分辨大致对不对，内容对不对最终靠逐字键入本身。
- 真实发送：第一条 `枢发送测试` 发出，群里只有一条，但发后确认太严，报了“不确定”，没有重发。第二条被打字核对误拦，没有发送，输入框已清空。前台记录是 Claude → 微信 → Claude，切回正常。放宽核对后再发，日志显示已发到群里，草稿从待确认消失。
- 没写草稿的一次（2026-11-05，Haiku）：对方只 @ 了一句“ok”，模型判断不用回复，没写草稿。提示词改成只要有 @ 就写以后，同样的聊天写出了 `收到，报告我会在【报告完成时间】前发出。`。这次读到 11 条，顺序对，无漏无重，概要也准。这句草稿有点多余，是否回复由主人决定。
- 成员列表（2026-11-05，只打字不按回车）：打 `@` 后弹出单独的工具窗口（类名以 `QWindowToolSaveBits` 结尾，273×215，在光标附近），主窗口保持前台。默认高亮第一行“所有人”（y=38 到 72，颜色 213,213,215，其他行 238,238,240），所以打完 `@` 绝不能按回车。打完名字后窗口缩成 273×110，只剩这一行且高亮。OCR 只有放大 1 倍时读对 `小号`，放大 2、3 倍什么都读不到。Esc 能关掉列表。
- 带 @ 的发送（2026-11-05）：逐字键入 `@小号 枢发送测试3`，消息发出了（5.4 秒），但用户在小号的设备上看，没有 @ 到，空格关掉了列表，留下的只是普通文字。改成打 `@`、等列表出现、打名字、核对高亮行、按回车选人、再打正文，`@小号 枢发送测试4` 用时 6.3 秒发出，用户确认小号成功被 @ 到。`@` 和名字连着快速打时列表来不及弹出。只测了 3 人群和两个字的名字。
- 草稿：第一版提示词写出“好的，我【周五下午】前把报告发到群里”，替主人答应了，也猜了括号里的内容。收紧后写出“收到，报告我【是否能周五前完成】，【预计交付时间】再同步大家”，没有替主人决定，但读着有点别扭。只测了 Haiku。
